(*) First lets understand the problem Karpenter solves

- Imagine your company runs an application on an Amazon EKS cluster
- Your cluster currently has:
    * 2 worker nodes (EC2 instances)
    * Each node has 4 CPUs and 8 GB RAM
    * Your application runs 4 pods
    * Each pod requests 1 CPU and 2 GB RAM

                                               Your Kubernetes cluster
            
              -----------------------------                                   -----------------------------             
              |  Worker Node 1 (Running)  |                                   |  Worker Node 2 (Running)  |
              |    4 CPU     8 GB RAM     |                                   |    4 CPU     8 GB RAM     |
              |---------------------------|                                   |---------------------------|
              |      Pod A – 1 CPU        |                                   |      Pod C – 1 CPU        |
              |      Pod B – 1 CPU        |                                   |      Pod D – 1 CPU        |
              |     2 CPU available       |                                   |     2 CPU available       |
              -----------------------------                                   -----------------------------
    Simplified example: actual scheduling also considers memory, Pod overhead, system reservations and other constraints.

- Now imagine traffic increases. Your Horizontal Pod Autoscaler (HPA) detects increased CPU usage and increases the application replicas from 4 to 8.
- So Kubernetes now needs to run 4 additional pods.

* But here's the problem:
What if the two existing worker nodes don't have enough available resources to run those new pods?
  - The new pods cannot be scheduled. They remain in the Pending state.
  - This is the problem we need to solve.

(*) Why isn't HPA enough?

- This is an important interview question.
- Remember these two responsibilities:

---------------------|-----------------------------------------------------------|
|    Component	     |            Responsibility                                 |
|--------------------|-----------------------------------------------------------|
|      HPA	         |   Increases or decreases the number of application pods   |
|  Node autoscaling	 |   Increases or decreases the number of worker nodes       |
----------------------------------------------------------------------------------

- HPA can request 10 Pods, but it cannot create additional EC2 instances to provide more computing capacity.
- For example:
    * HPA increases replicas from 4 to 10
    * Kubernetes tries to schedule the additional pods
    * Existing nodes don't have enough resources
    * Some Pods remain Pending
    * We need additional worker nodes
- This is where node autoscaling solutions come into the picture.

(*) How did companies solve this problem before Karpenter?
  - Before Karpenter became popular, many EKS clusters used two things:
      1. Amazon EC2 Auto Scaling Group (ASG)
      2. Kubernetes Cluster Autoscaler (CA)


1. Amazon EC2 Auto Scaling Group (ASG)
   - An Amazon EC2 Auto Scaling Group is an AWS service feature that automatically maintains a specified number of EC2 instances based on minimum, desired and maximum capacity settings.
   - For example, imagine an ASG configured as follows:

-----------------|---------|----------------------------------------|
Configuration	  |  Value	|               Meaning                  |
-----------------|---------|----------------------------------------|
Minimum capacity |	 2	   |   Maintain at least 2 EC2 instances    |
Desired capacity |    3	   |   Currently maintain 3 EC2 instances   |
Maximum capacity |	 6	   |   Allow up to 6 EC2 instances          |
-----------------|---------|----------------------------------------|

   - If the desired capacity increases from 3 to 5, ASG launches 2 additional EC2 instances.
   - Important: ASG manages EC2 instances, but it does not directly understand Kubernetes Pods or their scheduling requirements.


2. Kubernetes Cluster Autoscaler (CA)
   - Cluster Autoscaler is a Kubernetes component that automatically increases or decreases the number of worker nodes based on the resource requirements of Kubernetes Pods.
   - In AWS EKS, Cluster Autoscaler typically works with EC2 Auto Scaling Groups to manage worker node capacity.
   - Suppose your EKS cluster has:
         * 2 worker nodes
         * 5 application Pods running
         * HPA increases replicas from 5 to 10
         * Existing worker nodes don't have enough CPU or memory for all the new Pods
   - What happens?
         * Kubernetes scheduler tries to place the new Pods onto existing nodes
         * Some Pods remain Pending because there are insufficient resources
         * Cluster Autoscaler identifies these unschedulable Pods
         * It determines whether an existing configured node group can accommodate them
         * Cluster Autoscaler requests an increase in that node group's ASG desired capacity.
         * ASG launches additional EC2 instances.
         * Once those instances join the EKS cluster and become Ready, Kubernetes schedules the Pending Pods.

(*) Why wasn't Cluster Autoscaler enough?

- Cluster Autoscaler works well, but the traditional approach has limitations.
- Example: Imagine your company has three types of workloads:
      * Backend applications need general-purpose instances.
      * Redis needs memory-optimized instances.
      * ML applications need GPU instances.
- Your DevOps team might maintain three separate EKS node groups backed by ASGs.
- Cluster Autoscaler can scale these configured node groups, but it cannot automatically create an entirely new node group whenever a different EC2 instance 
type is required.
- This introduces additional node-group configuration and maintenance overhead.
- Karpenter addresses this by provisioning suitable EC2 instances directly based on Pod requirements and administrator-defined constraints, without requiring a pre-created ASG-backed node group for every instance choice.

(*) Interview-ready answer

- Before Karpenter, EKS clusters commonly used Kubernetes Cluster Autoscaler along with AWS Auto Scaling Groups to scale worker nodes.

- An ASG is an AWS feature that maintains EC2 instance capacity based on minimum, desired and maximum settings.

- Cluster Autoscaler is a Kubernetes component that monitors unschedulable Pods and determines whether additional worker nodes are required.

- When Pods cannot be scheduled due to insufficient resources, Cluster Autoscaler increases the desired capacity of a suitable configured ASG. AWS launches additional EC2 instances, which join the EKS cluster as worker nodes. Kubernetes then schedules the Pending Pods.

- One limitation is that Cluster Autoscaler primarily works with preconfigured node groups, whereas Karpenter can dynamically select and provision suitable EC2 instance types based on workload requirements.

- HPA: Scales the number of Pods.
- Cluster Autoscaler: Scales worker node capacity through configured node groups.
- ASG: Actually launches or terminates the EC2 instances in the traditional AWS setup.
