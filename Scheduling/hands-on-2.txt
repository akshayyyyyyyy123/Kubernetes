Step 04 — Required Node Affinity
- Now let's do something nodeSelector can't easily express.
- We want: Run on database OR frontend nodes.

# required-affinity.yaml

apiVersion: v1
kind: Pod
metadata:
  name: nginx-required-affinity-four
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: role
            operator: In
            values:
            - logging-role
            - database-role
  containers:
  - name: nginx
    image: nginx:alpine

# kubectl apply -f required-affinity.yaml
  
# kubectl get pod nginx-required-affinity -o wide                                                                                                   
NAME                      READY   STATUS             RESTARTS        AGE   IP       NODE           NOMINATED NODE   READINESS GATES
nginx-required-affinity   0/1     CrashLoopBackOff   9 (2m48s ago)   13m   <none>   minikube-m09   <none>           <none>

It can run on : minikube (ROLE: logging-role, NAME: master-node) OR minikube-m07 (ROLE: database-role, NAME: worker-node-07)

Step 06 — Preferred Node Affinity
- Now we test soft preference. Prefer the frontend node.

I have only two nodes running:

# kubectl get nodes -L role,name                                                                                                                      
NAME           STATUS   ROLES           AGE   VERSION   ROLE            NAME
minikube       Ready    control-plane   69d   v1.34.0   logging-role    master-node
minikube-m07   Ready    <none>          18d   v1.34.0   database-role   worker-node-07

apiVersion: v1
kind: Pod
metadata:
  name: nginx-preferred
spec:
  affinity:
    nodeAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        preference:
          matchExpressions:
          - key: role
            operator: In
            values:
            - frontend-role

  containers:
  - name: nginx
    image: nginx:alpine

- "I prefer a frontend node, but there isn't one. That's okay."
- So both nodes remain eligible:
    minikube       → logging-role   ✅
    minikube-m07   → database-role  ✅
- The Pod will therefore be scheduled on one of those two nodes.

  
Required + frontend doesn't exist
        ↓
❌ Pending

Preferred + frontend doesn't exist
        ↓
✅ Schedule on another eligible node

Step 7 — The best experiment 🔥

- Let's intentionally create a Pod that cannot currently be scheduled.
- Required: role=gpu
- But currently:
      minikube       logging
      minikube-m07   database
      minikube-m09   frontend
  
- Create gpu.yaml

apiVersion: v1
kind: Pod
metadata:
  name: nginx-gpu
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: role
            operator: In
            values:
            - gpu

  containers:
  - name: nginx
    image: nginx:alpine

# kubectl apply -f gpu.yaml
- In this case, the pod remains in "PENDING" state.

Required:
role=gpu

Current nodes:

logging    ❌
database   ❌
frontend   ❌

No match
   ↓
Pending

See the scheduler's explanation
# kubectl describe pod nginx-gpu
- Look at the Events section.
- You'll see a scheduling failure explaining that the nodes didn't satisfy the affinity requirements.
- This is extremely useful in real production debugging.
