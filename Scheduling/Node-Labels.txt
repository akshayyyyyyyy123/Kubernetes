(*) Why were Node Labels introduced?
  - Imagine your cluster has three worker nodes - Worker-1, Worker-2 and Worker-3. 
  - To Kubernetes, they're just nodes.
  - Example:
    
    Worker-1               Worker-2              Worker-3
     16 CPU                 4 CPU                GPU Enabled
    64 GB RAM              8 GB RAM

  - The question is how can kubernetes distinguish these nodes? It is using the labels.

------------------------------------------------------------------------------------------------------------------------------------------------------

(*) What is a Node Label?
  - A Node Label is a key-value pair attached to a Node that provides metadata about that node.
  - Example:
      disktype = ssd
      environment = prod
  - They are exactly like Pod labels. 
  - Pod labels describe Pods AND Node labels describe Nodes.

------------------------------------------------------------------------------------------------------------------------------------------------------

(*) Where are Node Labels stored?
  - It is a Kubernetes API object stored in the control plane.
  - The labels are stored in the metadata section of the Node object in the API server (and persisted in etcd through the API server).
  - When a worker node joins the cluster:
      * The kubelet on the worker node registers itself with the API Server.
      * The API Server creates a Node object.
      * That Node object is stored in etcd.
      * The kubelet continuously updates the Node object's status (Ready, CPU, Memory, conditions, etc.)


                Control Plane
        ┌─────────────────────────┐
        │ API Server              │
        │ etcd                    │
        │                         │
        │ Node Object             │
        │ ----------------------  │
        │ Name: minikube-m02      │
        │ Labels:                 │
        │   role=logging          │
        │ Status: Ready           │
        │ Capacity: CPU, Memory   │
        └─────────────────────────┘
                    ▲
                    │
             kubelet updates it
                    │
                    ▼
        ┌─────────────────────────┐
        │      Worker Node        │
        │                         │
        │ kubelet                 │
        │ kube-proxy              │
        │ containerd              │
        │ Pods                    │
        └─────────────────────────┘

**** Worker Node → The actual machine (VM, EC2 instance, Minikube node) ****
**** Node Object → A Kubernetes resource representing that machine ****

- A Node object is a Kubernetes API resource stored in the control plane (via the API Server and etcd). It represents a worker node in the cluster. 
The kubelet running on the worker node registers and continuously updates the Node object with status and resource information. This distinction becomes
very important later when we study the scheduler, because the scheduler never talks directly to the worker node—it schedules Pods based on the Node objects
it retrieves from the API Server.

(*) Why do we need labels?
    - Let's say: 
            Node1                 Node2                  Node3
        role=logging            role=database          role=frontend

    - Now an application says, "I only want to run on logging nodes."
    - Without labels its impossible. With labels, Kubernetes can identify the correct nodes.

  - These labels become the foundation for scheduling decisions.

          Node1

          ├── env=prod
          └── zone=b
          
          Node3
          │
          ├── role=frontend
          ├── env=test
          └── zone=a
