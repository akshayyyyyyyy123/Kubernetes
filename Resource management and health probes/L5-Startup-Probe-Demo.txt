Startup Probe
  Let's prove why a Startup Probe matters with a real Minikube experiment

------------------------------------------------------------------------------------------------------------------------------------------------------------

STEP 01 — Understand the scenario

- Imagine a Java application takes 60 seconds to initialize.
- If its liveness probe starts checking too early and fails repeatedly, Kubernetes may restart the container before the application finishes starting.
It could get stuck in a restart loop.
- A startup probe solves this: Kubernetes waits for the startup probe to succeed before running the liveness and readiness probes.

------------------------------------------------------------------------------------------------------------------------------------------------------------

STEP 02 — Create the YAML

apiVersion: v1
kind: Pod
metadata:
  name: startup-demo
spec:
  containers:
    - name: nginx
      image: nginx:alpine
      ports:
        - containerPort: 80

      startupProbe:
        httpGet:
          path: /
          port: 80
        periodSeconds: 5
        failureThreshold: 12

      livenessProbe:
        httpGet:
          path: /
          port: 80
        periodSeconds: 5
        failureThreshold: 3

      readinessProbe:
        httpGet:
          path: /
          port: 80
        periodSeconds: 5


What do these settings mean?
  - startupProbe: checks whether startup has completed.
  - failureThreshold: 12 × periodSeconds: 5: allows roughly 60 seconds of startup-probe failures before the startup probe fails and Kubernetes restarts
the container.
  - livenessProbe: checks whether the running application remains healthy.
  - readinessProbe: checks whether it can receive traffic.
  - The liveness and readiness probes won't begin until the startup probe succeeds.

STEP 03 - We'll deliberately configure a startup probe that fails so you can observe the restart behavior.

apiVersion: v1
kind: Pod
metadata:
  name: startup-demo
spec:
  containers:
    - name: nginx
      image: nginx:alpine
      ports:
        - containerPort: 80

      startupProbe:
        httpGet:
          path: /health
          port: 80
        periodSeconds: 5
        failureThreshold: 12

      livenessProbe:
        httpGet:
          path: /
          port: 80
        periodSeconds: 5
        failureThreshold: 3

      readinessProbe:
        httpGet:
          path: /
          port: 80
        periodSeconds: 5


# kubectl apply -f startup-probe.yaml
pod/startup-break-demo created

startup-break-demo   0/1     Running   2 (3s ago)   2m3s


What happened in your experiment?
          Startup probe failed: HTTP probe failed with statuscode: 404
          Container nginx failed startup probe, will be restarted

The sequence was:
  * The NGINX container started.
  * The startup probe sent HTTP GET requests to /health (or whichever path you configured).
  * NGINX returned 404 Not Found because that endpoint doesn't exist.
  * The startup probe failed 12 consecutive checks.
  * Kubelet terminated and restarted the container.
  * The same cycle repeated, resulting in RESTARTS = 2.
Your Pod still shows Running because its current container instance is running, even though Kubernetes has restarted it multiple times.

------------------------------------------------------------------------------------------------------------------------------------------------------------

The most important difference

--------------------------------------------------------------------------------|
Probe	                                What you observed                         |
--------------------------------------------------------------------------------|
Readiness	                      0/1 Running, restart count stays 0              |
Liveness	                    Container restarts after repeated probe failures  |
Startup	                    Container restarts when startup never succeeds      |
--------------------------------------------------------------------------------|

- When a startup probe is configured, Kubernetes does not run the liveness or readiness probes until the startup probe succeeds. This protects slow-starting 
applications from premature liveness restarts.
