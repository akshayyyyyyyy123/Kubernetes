Liveness probe
  - Now let's test the difference. With a liveness probe, repeated failures can cause Kubernetes to restart the container.

----------------------------------------------------------------------------------------------------------------------------------------------------------

Step 1 — Create liveness-probe.yaml

apiVersion: v1
kind: Pod
metadata:
  name: liveness-demo
spec:
  containers:
    - name: nginx
      image: nginx:alpine
      ports:
        - containerPort: 80
      livenessProbe:
        httpGet:
          path: /health
          port: 80
        initialDelaySeconds: 5
        periodSeconds: 5
        failureThreshold: 3

- We're deliberately using /health again because NGINX returns 404 for that path.
- Here, failureThreshold: 3 means Kubernetes will restart the container after three consecutive failed liveness checks, subject to the probe timing and any 
configured termination grace period.

Interpret your output

# kubectl get pod liveness-demo                                                                                                                       
NAME            READY   STATUS             RESTARTS        AGE
liveness-demo   0/1     CrashLoopBackOff   6 (2m18s ago)   6m4s

And the critical event:
  - Liveness probe failed: HTTP probe failed with statuscode: 404. Container nginx failed liveness probe, will be restarted
  - Kubelet sent GET /health to NGINX.
  - NGINX returned 404 because /health doesn't exist.
  - The liveness probe failed three consecutive times, reaching failureThreshold: 3.
  - Kubelet terminated and restarted the container.
  - The restart count increased to 3.

Important: Kubernetes restarted the container inside the existing Pod. It did not create a new Pod. That's why the Pod name remains liveness-demo.

Compare your two hands-on experiments

Observation                  	      Readiness probe	                    Liveness probe
Probe endpoint	                    /health	                              /health
HTTP response	                      404	                                   404
Pod readiness	                      0/1	                                 Can return to 1/1 after restart
Container restarted?	              No	                                    Yes
Restart count	                      0	                                       3
Pod replaced?                      	No	                                     No


****** 
    Why is liveness showing 1/1 despite failing? Because Kubernetes keeps restarting NGINX, and each new container briefly becomes ready according to the Pod's
    readiness state—there is no readiness probe configured on this Pod. A running container without a readiness probe is normally considered ready.
*******

This is a useful production lesson: a Pod can appear ready while its container is repeatedly restarting. Always inspect RESTARTS and Events, not just READY.
